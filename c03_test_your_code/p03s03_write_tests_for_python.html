Écrire des tests pour du code Python

Le projet support du chapitre demande d’écrire le même modèle géométrique deux fois : une fois en C++, une fois en Python. Les tests sont donc eux aussi écrits deux fois, et cela tombe bien : comparer les deux suites est la façon la plus rapide de comprendre ce qui, dans un test, relève du principe et ce qui relève de l’outil.

Cette section suppose la lecture de Écrire des tests C++ avec Google Test, dont elle reprend le vocabulaire (cas de test, fixture, tolérance, invariant, oracle) sans le redéfinir.

Le code à écrire côté Python est le pendant exact du code C++ :

unittest ou pytest : lequel utiliser ?

Deux outils coexistent dans l’écosystème Python, et tous deux sont utilisés par ROS 2.

unittest

pytest

Origine

bibliothèque standard de Python

paquet externe (python3-pytest)

Écriture d’un test

une méthode test_* dans une classe dérivant de unittest.TestCase

une simple fonction test_*, dans ou hors d’une classe

Vérifications

méthodes self.assertXxx(...)

le mot-clé assert de Python, réécrit pour afficher les valeurs

Contexte partagé

setUp / setUpClass

fixtures (décorateur @pytest.fixture), plus souples

Exécution

python3 -m unittest

pytest, qui sait aussi exécuter les tests unittest

Le point à retenir : pytest exécute les tests écrits avec unittest, l’inverse n’est pas vrai. Un test écrit en unittest est donc le choix le plus portable, et c’est celui du projet.

Note

Dans ROS 2, pytest est de toute façon présent : c’est lui qui exécute les tests des paquets ament_python et qui produit les rapports XML, que les tests soient écrits dans un style unittest ou non.

Structure d’un fichier de tests

Le fichier de tests Python du projet suit la même organisation que son équivalent C++ : une classe de base qui prépare le contexte, puis une classe par sujet.

Préparer le contexte : setUpClass

setUpClass est l’équivalent de SetUpTestSuite en gtest : il est appelé une seule fois pour la classe, ce qui permet de ne charger qu’une fois le modèle de simulation. setUp, lui, est appelé avant chaque méthode de test.

Code source 25 La classe de base, qui joue le rôle de la fixture C++
class MujocoTestCase(unittest.TestCase):
    """Fournit une simulation MuJoCo headless et la géométrie extraite du modèle."""

    @classmethod
    def setUpClass(cls):
        cls.sim = FiveBarsSim()
        cls.geometry = Geometry(**asdict(cls.sim.geometry))

    def simulate(self, q1: float, q4: float):
        """Asservit (q1, q4) dans MuJoCo depuis 'home' ; renvoie (q1, q4) mesurés et (x, y) du stylo."""
        self.sim.reset()
        self.assertTrue(self.sim.settle(q1, q4), "la simulation n'a pas convergé")
        self.assertLess(self.sim.closure_error(), 1e-6, "chaîne non fermée dans la simulation")
        q = self.sim.actuated_positions()
        pen = self.sim.pen_position()
        return (float(q[0]), float(q[1])), (float(pen[0]), float(pen[1]))

Comme en C++, la classe de base fournit une méthode d’aide simulate() qui amène la simulation à l’équilibre et vérifie au passage deux conditions de validité de la mesure. Et comme en C++, les classes de test dérivent de cette classe de base au lieu de dupliquer ce code.

Important

setUpClass est un @classmethod : il s’applique à la classe, donc les objets qu’il crée sont partagés par tous les tests de cette classe. Tout ce qui est partagé et mutable doit être remis à zéro par test — ici, c’est self.sim.reset(), appelé au début de simulate() et au début des tests qui lisent l’état initial. C’est la même exigence d’indépendance des tests qu’en C++, avec le même piège.

Les vérifications usuelles

Méthode

Usage

assertTrue(x) / assertFalse(x)

valeurs booléennes

assertEqual(a, b)

égalité exacte — jamais pour des flottants

assertAlmostEqual(a, b, delta=t)

égalité de flottants à t près : l’équivalent de EXPECT_NEAR

assertIsNone(x) / assertIsNotNone(x)

cas d’erreur et cas nominal des fonctions qui renvoient None

assertLess(a, b) / assertGreater(a, b)

comparaisons, par exemple une distance inférieure à une tolérance

assertRaises(Erreur)

vérifier qu’un appel lève bien une exception

np.testing.assert_allclose(a, b, atol=t)

comparer des tableaux de flottants élément par élément

Avertissement

assertAlmostEqual(a, b) sans argument delta compare à 7 décimales près, ce qui n’a aucun sens physique : 10-7 m est un dixième de micromètre. Indiquez toujours explicitement delta= (ou atol= pour numpy), avec la justification de sa valeur.

Les tolérances du projet sont, comme en C++, déclarées et commentées en un seul endroit, avec les mêmes valeurs :

Code source 26 Les tolérances, identiques à celles de la suite C++
POS_TOL = 1e-4      # 0.1 mm entre modèle et simulation
ANGLE_TOL = 1e-3    # rad
REACH_TOL = 5e-4    # 0.5 mm après asservissement simulé

Astuce

Les tolérances doivent être identiques dans les deux langages : les deux implémentations résolvent le même problème géométrique et sont jugées par la même référence. Si l’une des deux avait besoin d’une tolérance plus large pour passer, ce serait le signe d’une erreur dans cette implémentation, et non d’une particularité du langage.

Comparer des tableaux avec numpy

La position du stylo est un couple de coordonnées. numpy.testing.assert_allclose compare les deux éléments en une seule vérification et, en cas d’échec, affiche l’écart maximal et le nombre d’éléments en désaccord :

Code source 27 Comparaison d’un couple de coordonnées à la position mesurée dans la simulation
    def test_home_configuration(self):
        self.sim.reset()
        q = self.sim.actuated_positions()
        pen = self.sim.pen_position()
        result = forward_kinematics(float(q[0]), float(q[1]), self.geometry)
        self.assertIsNotNone(result)
        np.testing.assert_allclose(result, pen[:2], atol=POS_TOL)

Prudence

assert_allclose possède deux tolérances : atol (absolue) et rtol (relative, 0 par défaut sur assert_allclose… mais pas sur d’autres fonctions numpy, où elle vaut 10-7). Pour des longueurs en mètres, c’est la tolérance absolue qui a un sens physique : on veut 0,1 mm, pas « 0,1 % de la valeur », car près de l’origine une tolérance relative devient absurde. Précisez donc toujours atol=.

Boucler sur des données sans perdre le diagnostic : subTest

C’est l’équivalent Python de SCOPED_TRACE, et il est encore plus utile. Un test qui boucle sur 16 configurations s’arrêterait à la première erreur, et le rapport ne dirait pas laquelle. subTest résout les deux problèmes à la fois : chaque itération est signalée séparément, et la boucle continue après un échec.

Code source 28 Un balayage de l’espace de travail, chaque itération étant identifiée
    def test_matches_mujoco_simulation(self):
        for q1d, q4d in Q_GRID_DEG:
            with self.subTest(q1_deg=q1d, q4_deg=q4d):
                (q1, q4), pen = self.simulate(math.radians(q1d), math.radians(q4d))
                result = forward_kinematics(q1, q4, self.geometry)
                self.assertIsNotNone(result, "configuration atteignable déclarée impossible")
                np.testing.assert_allclose(result, pen, atol=POS_TOL)

Les paramètres passés à subTest apparaissent dans le rapport d’échec sous la forme (q1_deg=90.0, q4_deg=20.0). C’est ce qui explique une particularité des résultats que nous verrons plus bas : 10 tests déclarés peuvent produire 64 erreurs, car chaque sous-test compte.

Invariants et cas d’erreur

Les propriétés vérifiées sont exactement les mêmes qu’en C++ (voir Écrire des tests C++ avec Google Test) : un cas nominal, un balayage, un piège à erreur connue, un invariant et les cas d’erreur.

Code source 29 L’invariant IK ∘ FK = identité
    def test_inverse_of_forward_is_identity(self):
        for q1d, q4d in Q_GRID_DEG:
            with self.subTest(q1_deg=q1d, q4_deg=q4d):
                q1, q4 = math.radians(q1d), math.radians(q4d)
                x, y = forward_kinematics(q1, q4, self.geometry)
                r1, r4 = inverse_kinematics(x, y, self.geometry)
                self.assertAlmostEqual(wrap(r1 - q1), 0.0, delta=1e-9)
                self.assertAlmostEqual(wrap(r4 - q4), 0.0, delta=1e-9)
Code source 30 Les cas d’erreur — avec, en première ligne, un cas valide
    def test_unreachable_point_returns_none(self):
        self.assertIsNotNone(inverse_kinematics(0.07, 0.17, self.geometry))
        self.assertIsNone(inverse_kinematics(0.5, 0.5, self.geometry))   # trop loin
        self.assertIsNone(inverse_kinematics(0.0, 0.0, self.geometry))   # sur l'axe moteur

La première ligne de ce dernier test mérite d’être soulignée une seconde fois : sans elle, une fonction qui renverrait toujours None passerait le test. C’est une erreur classique, et elle est d’autant plus facile à commettre en Python que rien n’oblige une fonction à renvoyer quelque chose.

Rendre un fichier de tests exécutable seul

Les trois dernières lignes du fichier permettent de le lancer directement, sans colcon ni pytest :

if __name__ == "__main__":
    unittest.main(verbosity=2)

C’est un petit confort qui change la vie en phase de mise au point.

Intégrer les tests Python au paquet ROS 2

La façon de déclarer les tests dépend du type de paquet, et c’est une source d’erreurs fréquente.

Dans un paquet ament_cmake

five_bars_kinematics est un paquet ament_cmake (il contient du C++) qui fournit aussi un module Python. Le module est installé par ament_python_install_package, et les tests Python sont déclarés par ament_add_pytest_test :

Code source 31 CMakeLists.txt — un seul paquet déclare la bibliothèque C++, le module Python et les deux suites de tests
# --- Module Python équivalent ---
ament_python_install_package(${PROJECT_NAME})

# --- Tests : vérité terrain = simulation MuJoCo headless ---
if(BUILD_TESTING)
  find_package(ament_cmake_gtest REQUIRED)
  find_package(ament_cmake_pytest REQUIRED)
  find_package(five_bars_description REQUIRED)

  list(APPEND CMAKE_MODULE_PATH "${CMAKE_CURRENT_SOURCE_DIR}/cmake")
  find_package(MuJoCo REQUIRED)
  message(STATUS "MuJoCo : ${MuJoCo_LIBRARY} (version ${MuJoCo_VERSION})")

  # share/five_bars_description/cmake/.. -> share/five_bars_description
  get_filename_component(_desc_share "${five_bars_description_DIR}/.." ABSOLUTE)
  set(FIVE_BARS_MJCF "${_desc_share}/mjcf/five_bars.xml")

  ament_add_gtest(test_kinematics_cpp test/test_kinematics.cpp TIMEOUT 300)
  target_link_libraries(test_kinematics_cpp ${PROJECT_NAME} MuJoCo::MuJoCo)
  target_compile_definitions(test_kinematics_cpp PRIVATE FIVE_BARS_MJCF_PATH="${FIVE_BARS_MJCF}")

  ament_add_pytest_test(test_kinematics_py test/test_kinematics.py
    TIMEOUT 300
    ENV FIVE_BARS_MJCF=${FIVE_BARS_MJCF})
endif()

L’option ENV passe une variable d’environnement au test. C’est le pendant du target_compile_definitions utilisé pour le test C++ : dans les deux cas, le chemin du modèle de simulation est fourni par le système de compilation, et le test ne dépend donc pas du répertoire depuis lequel on le lance.

Les dépendances de test correspondantes sont déclarées dans le package.xml :

  <test_depend>ament_cmake_gtest</test_depend>
  <test_depend>ament_cmake_pytest</test_depend>
  <test_depend>five_bars_description</test_depend>
  <test_depend>five_bars_mujoco</test_depend>
  <test_depend>python3-numpy</test_depend>
  <!-- MuJoCo (C et Python) : pip install mujoco, voir docker/Dockerfile -->

Note

Dans un paquet ament_cmake, oublier ament_add_pytest_test est une erreur silencieuse : les tests ne sont pas exécutés, et colcon test affiche un succès. C’est exactement le genre de situation que détecte la commande ros2_view_tests_all mentionnée dans Lancer les tests de ROS2 et les analyser : elle liste tous les tests exécutés, y compris ceux qui passent, et permet donc de vérifier que vos tests sont bien pris en compte.

Les tests de style, déjà rencontrés

Les échecs flake8 analysés dans Lancer les tests de ROS2 et les analyser sont eux aussi des tests Python, ajoutés automatiquement par ROS 2 aux paquets qui déclarent ament_lint_auto / ament_flake8. Ils ne vérifient pas le comportement du code mais son style.

Ce sont les moins critiques, et il ne faut pour autant pas les laisser échouer : un paquet dont les tests sont rouges pour une raison de forme masque les échecs qui comptent. Le sujet du formatage automatique est traité dans Formater automatiquement le code, et L’outil pre-commit montre comment faire corriger ces erreurs avant même de valider un commit.

Lancer les tests Python

Via colcon, comme tous les autres tests :

colcon test --packages-select five_bars_kinematics --event-handlers console_direct+
colcon test-result --verbose

Directement, ce qui est bien plus rapide en phase de développement :

# toute la suite, en mode bavard (-v affiche le nom de chaque test)
python3 -m unittest discover -s src/five_bars_kinematics/test -p "test_*.py" -v

# une seule classe, ou un seul test
python3 -m unittest -v test_kinematics.TestForwardKinematics
python3 -m unittest -v test_kinematics.TestForwardKinematics.test_home_configuration

Ou avec pytest, dont la sélection par motif est très pratique :

pytest -v src/five_bars_kinematics/test/test_kinematics.py

# ne garder que les tests dont le nom contient "pen_offset"
pytest -v -k pen_offset src/five_bars_kinematics/test/

# s'arrêter au premier échec, et afficher la valeur des variables locales
pytest -x -l src/five_bars_kinematics/test/

Important

Lancés à la main, hors de colcon, ces tests ont besoin de savoir où sont le module à tester et le modèle de simulation. C’est le rôle de PYTHONPATH et de FIVE_BARS_MJCF :

export PYTHONPATH=$PWD/src/five_bars_mujoco:$PWD/src/five_bars_kinematics
export FIVE_BARS_MJCF=$PWD/src/five_bars_description/mjcf/five_bars.xml

Dans un espace de travail compilé, source install/setup.bash s’en charge pour PYTHONPATH, et le code de localisation du modèle trouve le fichier dans le paquet installé.

Le verdict porte sur la bonne cause. Les erreurs sont des NotImplementedError levées par kinematics.py : les tests échouent parce que le code n’existe pas, et non parce qu’ils sont mal écrits. Les deux tests de TestSimulationHarness passent, ce qui confirme que l’environnement et la référence sont corrects.

La trace désigne la ligne fautive. Chaque erreur donne la pile d’appels complète : la ligne du test (test_kinematics.py, ligne 79) et la ligne du code testé (kinematics.py, ligne 51). C’est l’avantage principal de Python sur le C++ en phase de mise au point.

« 10 tests, 64 erreurs » n’est pas une contradiction. Les méthodes de test sont au nombre de 10, mais celles qui bouclent avec subTest produisent une erreur par itération : 16 configurations × plusieurs tests, plus 12 cibles, d’où 64. Si vous voyez un nombre d’échecs supérieur au nombre de tests, c’est normal, et c’est même utile : cela signifie que vous saurez toutes les configurations qui posent problème, et pas seulement la première.

Astuce

NotImplementedError est signalé comme ERROR et non comme FAIL. La distinction est utile : un FAIL est une vérification qui a rendu un verdict négatif, un ERROR est une exception imprévue qui a interrompu le test. Un ERROR inattendu dans une suite habituellement verte évoque un problème d’environnement (dépendance manquante, fichier introuvable) plutôt qu’une régression du calcul.

Deux langages, une seule spécification

Pour finir, comparons les deux suites de tests. Les mécanismes diffèrent :

Google Test (C++)

unittest (Python)

TEST_F(Suite, Nom)

def test_nom(self) dans une classe

Contexte partagé par la suite

SetUpTestSuite()

setUpClass()

Contexte par test

SetUp()

setUp()

Absence de résultat

…mais les propriétés vérifiées sont identiques : mêmes 16 configurations, mêmes 12 cibles, mêmes tolérances, mêmes invariants, mêmes cas d’erreur, même oracle. C’est le signe que la spécification a été pensée indépendamment du langage, et c’est le véritable enseignement de ce double jeu de tests : les tests décrivent le problème, pas l’implémentation.

Ce découplage a une conséquence pratique très agréable : les deux implémentations sont comparables. Si la version C++ passe et la version Python échoue sur la même configuration et avec la même tolérance, l’erreur est dans la version Python — et non dans l’énoncé.

Exercices

  1. Prendre la mesure de l’état initial. Lancez les deux suites (five_bars_mujoco puis five_bars_kinematics). Combien de tests passent dans chacune ? Expliquez l’écart.

  2. Comprendre le décompte. Retrouvez par le calcul le nombre 64 d’erreurs à partir des listes Q_GRID_DEG et XY_TARGETS et des tests qui bouclent dessus.

  3. Observer l’effet de ``subTest``. Supprimez le with self.subTest(...) de test_matches_mujoco_simulation et relancez. Combien d’erreurs obtenez-vous ? Que perdez-vous dans le diagnostic ?

  4. Casser une tolérance. Dans test_home_configuration, remplacez atol=POS_TOL par rtol=POS_TOL (sans atol). Le test est-il plus sévère ou moins sévère ? Pourquoi est-ce dangereux pour un point proche de l’origine ?

  5. Vérifier qu’un test a des dents. Écrivez une implémentation Python de forward_kinematics qui place la pointe du stylo en A3, comme dans l’exercice 3 de Écrire des tests C++ avec Google Test. Les tests Python détectent-ils le même bug, avec les mêmes écarts que la version C++ ?

  6. Ajouter un test de cohérence inter-langages. Proposez un test qui vérifie que les implémentations C++ et Python donnent le même résultat à 10-12 près. Où le placeriez-vous, et quelle difficulté pratique faut-il résoudre ?
