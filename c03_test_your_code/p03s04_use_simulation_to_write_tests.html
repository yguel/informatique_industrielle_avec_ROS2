Utiliser la simulation pour écrire des tests

Les deux sections précédentes ont montré comment écrire un test, en C++ et en Python. Il reste la question la plus difficile, et celle qui est propre à la robotique : qui décide de la valeur attendue ?

Vérifier que 2 + 3 vaut 5 ne pose aucun problème. Vérifier qu’un modèle géométrique place la pointe d’un stylo en \((0{,}0734\ \mathrm{m},\ 0{,}2022\ \mathrm{m})\) en est un tout autre : il faut connaître la réponse avant d’écrire le code qui la calcule, et sans utiliser ce code. Le composant qui fournit cette réponse s’appelle un oracle, et cette section explique comment une simulation peut en tenir le rôle.

Le problème de l’oracle

Un test se compose toujours de trois éléments : des entrées, le code à tester, et une référence à laquelle comparer le résultat. C’est le troisième élément qui est difficile à obtenir.

Les stratégies possibles, et leurs limites

Oracle

Principe

Limite

Valeurs calculées à la main

on calcule quelques cas au crayon, ou sur la CAO

très peu de points, erreurs de calcul humaines, aucune couverture de l’espace de travail

Implémentation de référence

on compare à un code déjà validé (autre bibliothèque, code d’un collègue)

il faut déjà disposer d’une implémentation en laquelle on a confiance

Invariants

on vérifie des propriétés vraies pour toute entrée (IK ∘ FK = id)

deux fonctions toutes deux fausses mais réciproques passent le test

Mesures sur le robot réel

on bouge le robot et on mesure

lent, non reproductible, nécessite le matériel et un moyen de mesure externe

Simulation

un simulateur physique calcule le comportement du mécanisme

fidélité limitée au modèle ; il faut valider le simulateur lui-même

Aucune n’est suffisante seule, et les tests du projet 5 barres en combinent quatre : quelques valeurs issues de la CAO, des invariants, des cas d’erreur, et surtout une simulation comme référence principale.

Pourquoi le robot réel ne peut pas servir de test unitaire

C’est une tentation naturelle en robotique, et il faut y renoncer pour des raisons pratiques :

  1. Disponibilité : un seul robot pour un groupe d’étudiants, et aucun robot sur le serveur d’intégration continue.

  2. Vitesse : une suite de tests doit s’exécuter en quelques secondes pour être lancée à chaque modification. Le projet balaie 16 configurations et 12 cibles, soit une trentaine de mouvements complets — impossible à faire sur un robot à chaque sauvegarde de fichier.

  3. Reproductibilité : frottements, jeux, dérive thermique des servos et bruit de mesure font qu’une même consigne ne donne jamais deux fois exactement le même résultat. Un test qui n’est pas reproductible est un test instable.

  4. Risque : un modèle inverse faux envoie des consignes aberrantes. Sur un mécanisme à chaîne fermée comme le 5 barres, cela signifie forcer deux bras l’un contre l’autre — donc casser le matériel.

Important

Les tests sur le robot réel sont indispensables, mais ils ne jouent pas le même rôle. Ce sont des tests de validation (ou de recette) : peu nombreux, lancés rarement, exécutés à la main et sous surveillance. Les tests unitaires, eux, doivent être nombreux, rapides, reproductibles et automatiques : c’est là que la simulation est irremplaçable.

La simulation comme vérité terrain, et pourquoi c’est valide

L’objection évidente est la suivante : si je teste mon modèle avec un autre modèle, je ne teste rien. Elle serait fondée si les deux calculaient la même chose de la même façon. Toute la validité du dispositif repose sur le fait que ce n’est pas le cas.

Les deux n’ont en commun que les paramètres géométriques — et ceux-ci sont lus dans un fichier unique, ce qui est précisément ce que l’on veut (voir plus bas). Une erreur de trigonométrie, de signe, de convention d’angle, de mode d’assemblage ou d’oubli du décalage du stylo n’a aucune raison de se produire à l’identique dans les deux chemins. C’est ce qui rend la comparaison informative.

Astuce

Le principe se généralise bien au-delà de la robotique : un oracle est utile quand il est indépendant du code testé, pas quand il est « plus juste ». Comparer deux implémentations qui partagent la même formule ne prouve rien ; comparer une formule fermée à une résolution numérique, ou un algorithme optimisé à une version naïve et lente, prouve beaucoup.

La simulation « headless »

La simulation utilisée par les tests tourne sans affichage (headless) : pas de fenêtre, pas d’OpenGL, pas d’interaction. Ce n’est pas un détail d’implémentation, c’est une condition pour que les tests soient automatisables :

  • ils peuvent tourner sur un serveur d’intégration continue, qui n’a ni écran ni carte graphique (voir Exécuter les tests automatiquement : l’intégration continue) ;

  • ils tournent beaucoup plus vite que le temps réel : un balayage des 16 configurations, soit 16 mouvements complets amenés à l’équilibre, coûte une soixantaine de millisecondes en C++, et la suite entière reste sous la seconde ;

  • aucune dépendance graphique n’est nécessaire, ce qui simplifie l’image Docker.

C’est pourquoi le projet sépare soigneusement la simulation (sim.py, mujoco_five_bars.hpp) de son affichage (direct_gui.py, le viewer du sim_node). Cette séparation est une règle de conception générale : le calcul ne doit jamais dépendre de son affichage, sinon il devient intestable.

// Sert de vérité terrain aux tests du modèle géométrique : on asservit (q1, q4)

class MujocoFiveBars
{
public:
  explicit MujocoFiveBars(const std::string & path = modelPath())
  {
    char error[1024] = "";
    model_ = mj_loadXML(path.c_str(), nullptr, error, sizeof(error));
    if (!model_) {
      throw std::runtime_error("Chargement MJCF impossible (" + path + ") : " + error);
    }
    data_ = mj_makeData(model_);
    q1_adr_ = model_->jnt_qposadr[id(mjOBJ_JOINT, "joint_q1")];
    q4_adr_ = model_->jnt_qposadr[id(mjOBJ_JOINT, "joint_q4")];
    act_q1_ = id(mjOBJ_ACTUATOR, "act_q1");
    act_q4_ = id(mjOBJ_ACTUATOR, "act_q4");
    pen_ = id(mjOBJ_SITE, "pen_tip");
    a3_l2_ = id(mjOBJ_SITE, "A3_link2");
    a3_l3_ = id(mjOBJ_SITE, "A3_link3");
    reset();
  }

  ~MujocoFiveBars()
  {
    mj_deleteData(data_);
    mj_deleteModel(model_);
  }

  MujocoFiveBars(const MujocoFiveBars &) = delete;
  MujocoFiveBars & operator=(const MujocoFiveBars &) = delete;

  /// Retour à la configuration 'home' (assemblage CAO) puis stabilisation.
  void reset()
  {
    mj_resetDataKeyframe(model_, data_, id(mjOBJ_KEY, "home"));
    mj_forward(model_, data_);
    for (int i = 0; i < 300; ++i) {  // referme exactement la chaîne (keyframe approximative)
      mj_step(model_, data_);
    }
  }

  /// Asservit les servos simulés sur (q1, q4) : rampe de consigne (suivi continu de la
  /// branche d'assemblage), maintien, puis attente de l'équilibre. Renvoie true si convergé.
  bool settle(double q1, double q4, double ramp_time = 0.4, double hold_time = 0.6)
  {
    const double dt = model_->opt.timestep;
    const double c1 = data_->ctrl[act_q1_], c4 = data_->ctrl[act_q4_];
    const int n_ramp = std::max(1, static_cast<int>(ramp_time / dt));
    for (int k = 1; k <= n_ramp; ++k) {
      const double s = static_cast<double>(k) / n_ramp;
      data_->ctrl[act_q1_] = c1 + s * (q1 - c1);
      data_->ctrl[act_q4_] = c4 + s * (q4 - c4);
      mj_step(model_, data_);
    }
    for (int k = 0; k < static_cast<int>(hold_time / dt); ++k) {
      mj_step(model_, data_);
    }
    for (int k = 0; k < 5000; ++k) {
      double vmax = 0.0;
      for (int i = 0; i < model_->nv; ++i) {
        vmax = std::max(vmax, std::abs(data_->qvel[i]));
      }
      if (vmax < 1e-4) {
        return true;
      }
      mj_step(model_, data_);
    }
    return false;
  }

  five_bars_kinematics::JointAngles measuredAngles() const
  {
    return {data_->qpos[q1_adr_], data_->qpos[q4_adr_]};
  }

  five_bars_kinematics::PenPosition penPosition() const
  {
    return {data_->site_xpos[3 * pen_], data_->site_xpos[3 * pen_ + 1]};
  }

  std::array<double, 2> siteXY(const std::string & name) const
  {
    const int s = id(mjOBJ_SITE, name);
    return {data_->site_xpos[3 * s], data_->site_xpos[3 * s + 1]};
  }

  double closureError() const
  {
    const double * a = data_->site_xpos + 3 * a3_l2_;
    const double * b = data_->site_xpos + 3 * a3_l3_;
    return std::sqrt(
      (a[0] - b[0]) * (a[0] - b[0]) + (a[1] - b[1]) * (a[1] - b[1]) + (a[2] - b[2]) * (a[2] - b[2]));
  }

  /// Paramètres géométriques lus dans le modèle MuJoCo (source de vérité des tests).
  five_bars_kinematics::Geometry geometry() const
  {
    auto body_x = [this](const char * n) {return model_->body_pos[3 * id(mjOBJ_BODY, n)];};
    auto site_pos = [this](const char * n, int k) {return model_->site_pos[3 * id(mjOBJ_SITE, n) + k];};
    const double l2 = site_pos("A3_link2", 0);
    return {
      body_x("link4") - body_x("link1"), body_x("link2"), l2, site_pos("A3_link3", 0),
      body_x("link3"), site_pos("pen_tip", 0) - l2, site_pos("pen_tip", 1)};
  }

  const mjModel * model() const {return model_;}

private:
  int id(mjtObj type, const std::string & name) const
  {
    const int i = mj_name2id(model_, type, name.c_str());
    if (i < 0) {
      throw std::runtime_error("Élément MuJoCo introuvable : " + name);
    }
    return i;
  }

  mjModel * model_{nullptr};
  mjData * data_{nullptr};
  int q1_adr_{}, q4_adr_{}, act_q1_{}, act_q4_{}, pen_{}, a3_l2_{}, a3_l3_{};
};

}  // namespace five_bars_test

#endif  // FIVE_BARS_KINEMATICS__TEST__MUJOCO_FIVE_BARS_HPP_

La configuration de référence (home) est l’assemblage mesuré sur la CAO. Mais une configuration d’assemblage saisie à la main n’est jamais exactement fermée : les 300 pas de simulation laissent la contrainte en A3 se refermer précisément. C’est une illustration de ce que doit faire une remise à zéro : non pas « recopier des valeurs », mais rétablir toutes les invariants de l’état initial.

Amener le mécanisme à l’équilibre, et savoir si on y est arrivé.

Trois points essentiels pour la reproductibilité :

  1. La consigne est appliquée en rampe (ramp_time) et non en échelon. Un échelon ferait traverser le mécanisme à grande vitesse et pourrait le faire basculer sur l”autre mode d’assemblage : la mesure ne correspondrait plus à la configuration demandée. La rampe suit continûment la branche d’assemblage courante.

  2. La fonction attend que les vitesses soient toutes inférieures à un seuil, c’est-à-dire que l’équilibre soit effectivement atteint — et pas qu’un temps arbitraire se soit écoulé.

  3. Elle renvoie un booléen : si l’équilibre n’est pas atteint au bout de 5000 pas, elle le signale au lieu de renvoyer une mesure silencieusement fausse.

La contrainte de fermeture de MuJoCo est résolue numériquement : elle n’est jamais exactement satisfaite. closureError() donne la distance résiduelle entre les deux points A3, ce qui permet aux tests de vérifier la qualité de leur propre référence avant de s’en servir.

Ces deux vérifications sont justement ce que la fixture fait systématiquement, avant de rendre la main au test :

Code source 37 Toute mesure est accompagnée de la vérification de ses conditions de validité
  /// Asservit (q1, q4) depuis 'home' ; renvoie les angles mesurés et la position du stylo.
  std::pair<JointAngles, PenPosition> simulate(double q1, double q4)
  {
    sim_->reset();
    EXPECT_TRUE(sim_->settle(q1, q4)) << "la simulation n'a pas convergé";
    EXPECT_LT(sim_->closureError(), 1e-6) << "chaîne non fermée dans la simulation";

Important

C’est le point le plus transposable de cette section : un oracle doit pouvoir dire qu’il ne sait pas. Sans les deux vérifications ci-dessus, une simulation qui n’aurait pas convergé fournirait une position parfaitement plausible mais fausse, et le test accuserait le modèle de l’étudiant. Un test qui accuse le mauvais coupable est un test nuisible.

"""Simulation MuJoCo du système 5 barres (sans dépendance ROS).

Conventions (voir five_bars_description/config/geometry.yaml) :
  * repère R0 : origine A1, x0 vers A5, z0 vers le haut ;
  * q1 = valeur de joint_q1 = angle ABSOLU du bras gauche (A1A2) par rapport à x0 ;
  * q4 = valeur de joint_q4 = angle ABSOLU du bras droit  (A5A4) par rapport à x0 ;
  * joint_A2, joint_A4 : pivots passifs (angles relatifs) ;
  * la boucle est fermée en A3 par une contrainte d'égalité MuJoCo (connect).
"""
from __future__ import annotations

import os
from dataclasses import dataclass

import mujoco
import numpy as np

ACTUATED_JOINTS = ("joint_q1", "joint_q4")
PASSIVE_JOINTS = ("joint_A2", "joint_A4")
ALL_JOINTS = ("joint_q1", "joint_A2", "joint_q4", "joint_A4")


def default_model_path() -> str:
    """Chemin du MJCF : $FIVE_BARS_MJCF, sinon le paquet ROS installé, sinon l'arbre source."""
    env = os.environ.get("FIVE_BARS_MJCF")
    if env:
        return env
    try:
        from ament_index_python.packages import get_package_share_directory

        return os.path.join(get_package_share_directory("five_bars_description"), "mjcf", "five_bars.xml")
    except Exception:  # pas de ROS ou paquet non installé
        here = os.path.dirname(os.path.abspath(__file__))
        return os.path.normpath(os.path.join(here, "..", "..", "five_bars_description", "mjcf", "five_bars.xml"))

@dataclass
class FiveBarsGeometry:
    """Paramètres géométriques (m) extraits du modèle MuJoCo — source de vérité des tests."""

    l0: float
    l1: float
    l2: float
    l3: float
    l4: float
    pen_dx: float  # décalage du stylo / A3, le long de A2->A3
    pen_dy: float  # décalage du stylo / A3, perpendiculaire (à gauche de A2->A3)

    @classmethod
    def from_model(cls, model: mujoco.MjModel) -> "FiveBarsGeometry":
        body = lambda n: model.body(n).pos  # noqa: E731
        site = lambda n: model.site(n).pos  # noqa: E731
        l2 = float(site("A3_link2")[0])
        return cls(
            l0=float(body("link4")[0] - body("link1")[0]),
            l1=float(body("link2")[0]),
            l2=l2,
            l3=float(site("A3_link3")[0]),
            l4=float(body("link3")[0]),
            pen_dx=float(site("pen_tip")[0] - l2),
            pen_dy=float(site("pen_tip")[1]),
        )


class FiveBarsSim:
    """Encapsule un modèle MuJoCo du 5 barres : commande (q1, q4), pas de simulation, états."""

    #: vitesse maximale des servos (rad/s) — AX-12A à vide : 59 tr/min ≈ 6.2 rad/s
    DEFAULT_MAX_SPEED = 6.0

    def __init__(self, model_path: str | None = None, max_speed: float | None = DEFAULT_MAX_SPEED):
        """max_speed : limitation de vitesse de la consigne (rad/s), None pour un échelon brut."""
        self.max_speed = max_speed
        self.model_path = model_path or default_model_path()
        self.model = mujoco.MjModel.from_xml_path(self.model_path)
        self.data = mujoco.MjData(self.model)
        m = self.model
        self._qadr = {j: int(m.jnt_qposadr[m.joint(j).id]) for j in ALL_JOINTS}
        self._dadr = {j: int(m.jnt_dofadr[m.joint(j).id]) for j in ALL_JOINTS}
        self._act = [m.actuator("act_q1").id, m.actuator("act_q4").id]
        self._pen = m.site("pen_tip").id
        self._s2 = m.site("A3_link2").id
        self._s3 = m.site("A3_link3").id
        self.geometry = FiveBarsGeometry.from_model(m)
        self.reset()

    # ------------------------------------------------------------------ état
    def reset(self) -> None:
        """Remet la simulation dans la configuration 'home' (assemblage CAO), chaîne refermée."""
        mujoco.mj_resetDataKeyframe(self.model, self.data, self.model.key("home").id)
        self.solve_closure()
        self._target = self.actuated_positions()
        self.data.ctrl[self._act] = self._target
        mujoco.mj_forward(self.model, self.data)

    @property
    def time(self) -> float:
        return float(self.data.time)

    @property
    def timestep(self) -> float:
        return float(self.model.opt.timestep)

    def ctrl_range(self, joint: str) -> tuple[float, float]:
        a = self._act[ACTUATED_JOINTS.index(joint)]
        lo, hi = self.model.actuator_ctrlrange[a]
        return float(lo), float(hi)

    def actuated_positions(self) -> np.ndarray:
        return np.array([self.data.qpos[self._qadr[j]] for j in ACTUATED_JOINTS])

    def actuated_velocities(self) -> np.ndarray:
        return np.array([self.data.qvel[self._dadr[j]] for j in ACTUATED_JOINTS])

    def actuated_efforts(self) -> np.ndarray:
        return np.array(self.data.actuator_force[self._act])

    def joint_positions(self) -> dict[str, float]:
        return {j: float(self.data.qpos[self._qadr[j]]) for j in ALL_JOINTS}

    def joint_velocities(self) -> dict[str, float]:
        return {j: float(self.data.qvel[self._dadr[j]]) for j in ALL_JOINTS}

    def pen_position(self) -> np.ndarray:
        """Position (x, y, z) de la pointe du stylo dans R0 (m)."""
        return self.data.site_xpos[self._pen].copy()

    def closure_error(self) -> float:
        return float(np.linalg.norm(self.data.site_xpos[self._s2] - self.data.site_xpos[self._s3]))

    # ------------------------------------------------------------ commande
    def set_command(self, q1: float, q4: float) -> tuple[float, float]:
        """Consigne de position des deux servos (rad, angles absolus). Saturée aux débattements.

        La consigne effectivement appliquée aux actionneurs rejoint cette cible à
        ``max_speed`` rad/s au plus (comme le 'moving speed' d'un Dynamixel).
        """
        cmd = []
        for j, q in zip(ACTUATED_JOINTS, (q1, q4)):
            lo, hi = self.ctrl_range(j)
            cmd.append(float(np.clip(q, lo, hi)))
        self._target = np.array(cmd)
        if self.max_speed is None:
            self.data.ctrl[self._act] = self._target
        return cmd[0], cmd[1]

    def command(self) -> tuple[float, float]:
        """Dernière consigne demandée (cible)."""
        return float(self._target[0]), float(self._target[1])

    def step(self, n: int = 1) -> None:
        """Avance la simulation de n pas (en appliquant la limitation de vitesse de consigne)."""
        m, d = self.model, self.data
        if n <= 0:
            return
        if self.max_speed is None or np.array_equal(d.ctrl[self._act], self._target):
            mujoco.mj_step(m, d, nstep=n)
            return
        dmax = self.max_speed * m.opt.timestep
        for k in range(n):
            delta = self._target - d.ctrl[self._act]
            if not delta.any():
                mujoco.mj_step(m, d, nstep=n - k)
                return
            d.ctrl[self._act] += np.clip(delta, -dmax, dmax)
            mujoco.mj_step(m, d)

    def settle(self, q1: float, q4: float, ramp_time: float = 0.4, hold_time: float = 0.6,
               vel_tol: float = 1e-4, max_time: float = 5.0) -> bool:
        """Simulation (dynamique) jusqu'à l'équilibre sur la consigne (q1, q4).

        La consigne est interpolée linéairement pendant ``ramp_time`` pour suivre
        continûment la branche d'assemblage courante. Renvoie True si l'équilibre
        est atteint (vitesses < vel_tol rad/s).
        """
        q_start = np.array(self.command())
        q_goal = np.array([q1, q4])
        n_ramp = max(1, int(ramp_time / self.timestep))
        for k in range(1, n_ramp + 1):
            self.set_command(*(q_start + (q_goal - q_start) * k / n_ramp))
            self.step()
        self.step(int(hold_time / self.timestep))
        t_end = self.time + max_time
        while self.time < t_end:
            if np.max(np.abs(self.data.qvel)) < vel_tol:
                return True
            self.step(10)
        return False

    # ------------------------------------------------- fermeture cinématique
    def solve_closure(self, q1: float | None = None, q4: float | None = None,
                      tol: float = 1e-10, max_iter: int = 50) -> bool:
        """Résout la fermeture de chaîne : (q1, q4) imposés, calcule les pivots passifs.

        Méthode de Newton (moindres carrés) sur les angles passifs, en utilisant le
        modèle MuJoCo pour la cinématique des sites A3 (positions + jacobiennes).
        Part de la configuration courante (garde donc la branche d'assemblage).
        Modifie data.qpos et met les vitesses à zéro. Renvoie True si convergé.
        """
        m, d = self.model, self.data
        if q1 is not None:
            d.qpos[self._qadr["joint_q1"]] = q1
        if q4 is not None:
            d.qpos[self._qadr["joint_q4"]] = q4
        cols = [self._dadr[j] for j in PASSIVE_JOINTS]
        qcols = [self._qadr[j] for j in PASSIVE_JOINTS]
        jac2 = np.zeros((3, m.nv))
        jac3 = np.zeros((3, m.nv))
        ok = False
        for _ in range(max_iter):
            mujoco.mj_kinematics(m, d)
            mujoco.mj_comPos(m, d)
            err = d.site_xpos[self._s2] - d.site_xpos[self._s3]
            if np.linalg.norm(err) < tol:
                ok = True
                break
            mujoco.mj_jacSite(m, d, jac2, None, self._s2)
            mujoco.mj_jacSite(m, d, jac3, None, self._s3)
            j = (jac2 - jac3)[:2, cols]  # mécanisme plan : x, y
            dq, *_ = np.linalg.lstsq(j, -err[:2], rcond=None)
            d.qpos[qcols] += dq
        d.qvel[:] = 0.0
        mujoco.mj_forward(m, d)
        return ok

    def closure_velocities(self, dq1: float, dq4: float) -> tuple[float, float]:
        """Vitesses des pivots passifs (joint_A2, joint_A4) compatibles avec la fermeture.

        La contrainte de fermeture s'écrit J_a dq_a + J_p dq_p = 0 (vitesse relative
        nulle des sites A3), d'où dq_p = -J_p^+ J_a dq_a. À appeler après solve_closure().
        """
        m, d = self.model, self.data
        jac2 = np.zeros((3, m.nv))
        jac3 = np.zeros((3, m.nv))
        mujoco.mj_jacSite(m, d, jac2, None, self._s2)
        mujoco.mj_jacSite(m, d, jac3, None, self._s3)
        j = (jac2 - jac3)[:2]
        ja = j[:, [self._dadr[n] for n in ACTUATED_JOINTS]]
        jp = j[:, [self._dadr[n] for n in PASSIVE_JOINTS]]
        dqp, *_ = np.linalg.lstsq(jp, -ja @ np.array([dq1, dq4]), rcond=None)
        return float(dqp[0]), float(dqp[1])

"""Tests (qui PASSENT) du modèle de simulation : sanity checks du MJCF et du solveur de fermeture."""
import math
import unittest

import numpy as np

from five_bars_mujoco.sim import FiveBarsSim


class TestFiveBarsSim(unittest.TestCase):
    @classmethod
    def setUpClass(cls):
        cls.sim = FiveBarsSim()

    def setUp(self):
        self.sim.reset()

    def test_home_is_closed(self):
        self.assertLess(self.sim.closure_error(), 1e-9)

    def test_settle_reaches_command_and_keeps_chain_closed(self):
        for q1, q4 in [(2.4, 0.9), (1.2, 0.5), (2.0, 1.6)]:
            self.assertTrue(self.sim.settle(q1, q4))
            np.testing.assert_allclose(self.sim.actuated_positions(), [q1, q4], atol=1e-4)
            self.assertLess(self.sim.closure_error(), 1e-6)

    def test_command_is_saturated(self):
        q1, q4 = self.sim.set_command(10.0, -10.0)
        self.assertEqual((q1, q4), (self.sim.ctrl_range("joint_q1")[1], self.sim.ctrl_range("joint_q4")[0]))

    def test_kinematic_closure_matches_dynamic_simulation(self):
        self.assertTrue(self.sim.settle(2.2, 1.3))
        dyn = self.sim.joint_positions()
        kin = FiveBarsSim(self.sim.model_path)
        self.assertTrue(kin.solve_closure(dyn["joint_q1"], dyn["joint_q4"]))
        for j, v in kin.joint_positions().items():
            self.assertAlmostEqual(v, dyn[j], delta=1e-5, msg=j)

    def test_unreachable_configuration_is_reported(self):
        kin = FiveBarsSim(self.sim.model_path)
        # bras croisés : A2 et A4 quasi confondus, |A2A4| < |l2 - l3| -> fermeture impossible
        self.assertFalse(kin.solve_closure(math.radians(30), math.radians(150)))


if __name__ == "__main__":
    unittest.main()

Une seule source de vérité pour la géométrie

Un piège subtil guette ce genre de test : si le code testé et son oracle tiennent chacun leur propre copie des dimensions du robot, les tests échoueront dès que l’une des deux copies changera — et, pire, ils pourront passer alors que le code est faux, parce que les deux copies seront fausses ensemble.

Le projet évite ce piège en désignant un fichier unique comme source de vérité :

Prudence

Cette technique a une contrepartie qu’il faut connaître : les tests ne vérifient plus les valeurs des cotes. Une erreur de saisie dans geometry.yaml donnerait un robot simulé différent du robot réel, et tous les tests passeraient. C’est exactement ce que rattrape test_home_pen_position_matches_cad, en comparant à une mesure indépendante faite sur la CAO. Toute « source unique de vérité » doit ainsi être confrontée, au moins en un point, à une mesure extérieure.

Deux commentaires de deux mots portent ici toute la réflexion.

« loin des singularités ». Un mécanisme à chaîne fermée possède des configurations où les bras sont alignés : le mécanisme y perd un degré de liberté, le modèle inverse y devient mal conditionné et la simulation y converge mal. Tester au voisinage d’une singularité ne renseigne ni sur le modèle ni sur la simulation : on y mesure l’instabilité numérique des deux. Les 16 configurations retenues sont donc choisies dans un domaine sain.

« une zone de dessin » (xyTargets). Les 12 cibles du modèle inverse ne sont pas prises au hasard : ce sont des points du rectangle dans lequel le robot est censé dessiner, c’est-à-dire le domaine d’usage réel. Un test doit couvrir ce que le code fera en production.

Astuce

Les singularités et les bords de l’espace de travail ne doivent pas être ignorés pour autant : ils doivent faire l’objet de tests dédiés, qui vérifient que le code les détecte (en renvoyant std::nullopt / None) au lieu de produire un résultat douteux. C’est le rôle des tests de cas d’erreur du projet.

Choisir les tolérances

Une simulation introduit ses propres erreurs : pas d’intégration fini, résidu de la contrainte de fermeture, raideur finie de l’asservissement. Les tolérances doivent donc être choisies au-dessus de ces erreurs, et bien en-dessous de l’erreur qu’on veut détecter.

Tolérance

Valeur

Ce qu’elle doit absorber, et rien de plus

kPosTol

0,1 mm

Résidu de la contrainte de fermeture et arrondis. Compare deux calculs de la même position d’équilibre.

kAngleTol

10-3 rad

Idem, propagé à travers le modèle inverse, où une petite erreur de position se traduit par une erreur d’angle d’autant plus grande que le bras de levier est court.

kReachTol

0,5 mm

Ajoute l”erreur statique de l’asservissement : les servos simulés sont des actionneurs de position de raideur finie (8 N·m/rad), qui ne rejoignent donc pas exactement leur consigne sous charge.

identité IK ∘ FK

10-9 rad

Aucune simulation n’intervient : deux calculs analytiques enchaînés, seul l’arrondi machine est admissible.

La leçon à retenir est que ces quatre valeurs ne sont pas quatre réglages du même test, mais quatre exigences différentes, chacune justifiée par la chaîne de calcul qu’elle juge. Quand un test échoue de peu, la bonne question n’est jamais « de combien faut-il relâcher la tolérance ? » mais « quelle source d’erreur ai-je oubliée dans mon raisonnement ? ».

Ce que la simulation ne testera jamais

Il serait malhonnête de terminer sans dire ce que ce dispositif ne couvre pas. L’écart entre la simulation et la réalité (sim-to-real gap) laisse passer :

  • les écarts de fabrication : les cotes réelles de votre exemplaire diffèrent de la CAO — c’est d’ailleurs pourquoi le projet mesure la CAO plutôt que de recopier le schéma du cours, et pourquoi geometry.yaml est modifiable ;

  • les jeux, frottements et souplesses non modélisés des liaisons ;

  • le comportement réel des servos : zone morte, résolution finie du codeur, saturation de couple, échauffement ;

  • tout ce qui touche à la communication avec le matériel : latence du bus Dynamixel, pertes de paquets, erreurs de conversion d’unités entre le pilote et le modèle ;

  • les erreurs de convention partagées entre le modèle et la simulation : si le MJCF et votre code utilisent tous deux une origine d’angle décalée de la même façon par rapport au robot réel, aucun test ne le verra.

Avertissement

Des tests unitaires verts ne signifient donc pas que le robot va dessiner correctement. Ils signifient quelque chose de plus modeste, mais de très utile : le modèle géométrique n’est plus un suspect. Quand le robot réel se comportera mal, vous pourrez chercher la cause ailleurs — dans la calibration, le pilote, les unités ou la mécanique — au lieu de douter de tout à la fois. C’est exactement ce que l’on attend d’une bonne suite de tests : réduire l’espace des causes possibles.

C’est pourquoi la pyramide complète comporte plusieurs étages, dont ce chapitre ne construit que la base :

  1. tests unitaires sur la simulation headless : nombreux, rapides, automatiques, à chaque push ;

  2. tests d’intégration avec ros2_control et les nœuds, toujours en simulation (le projet fournit ros2_control_sim.launch.py avec l’option use_viewer:=false) ;

  3. tests de validation sur le robot réel : rares, manuels, surveillés, et documentés.

Exercices

  1. Faire tourner l’oracle seul. Lancez les tests de five_bars_mujoco. En quoi diffèrent-ils, par leur objet, des tests de five_bars_kinematics ?

  2. Casser l’oracle. Dans geometry.yaml, remplacez l2 par 0.146300 (la cote du schéma du cours au lieu de celle de la CAO) et régénérez le modèle avec tools/generate_models.py. Quels tests échouent, et lesquels passent toujours ? Expliquez précisément pourquoi test_home_pen_position_matches_cad est celui qui détecte le problème.

  3. Supprimer la rampe. Dans settle, remplacez la rampe par un échelon (ramp_time très petit, ou max_speed=None côté Python) et observez les configurations extrêmes. Que se passe-t-il, et en quoi cela rendrait-il les tests non reproductibles ?

  4. Ignorer la convergence. Modifiez la fixture pour ne plus vérifier la valeur de retour de settle() ni l’erreur de fermeture, puis réduisez fortement le nombre de pas de la boucle d’attente. Les tests échouent-ils franchement, ou de façon trompeuse ? Quelle est la leçon ?

  5. Évaluer l’indépendance de l’oracle. Serait-il acceptable de tester le modèle direct en comparant son résultat à solve_closure() de FiveBarsSim ? Et au modèle inverse du même auteur ? Justifiez dans les deux cas en termes d’indépendance.

  6. Concevoir un test de validation. Proposez un protocole de test sur le robot réel qui vérifie le modèle géométrique direct. Quel moyen de mesure utiliseriez-vous ? Quelle tolérance viseriez-vous, et pourquoi ne peut-elle pas être de 0,1 mm ?
