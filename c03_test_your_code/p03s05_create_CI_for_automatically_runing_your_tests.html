Exécuter les tests automatiquement : l’intégration continue

Une suite de tests n’a de valeur que si elle est effectivement exécutée. Or un test lancé à la main est un test qu’on oublie de lancer : le jour où l’on est pressé, où l’on « ne touche qu’à un détail », ou simplement sur la machine d’un collègue dont l’environnement diffère du nôtre.

L”intégration continue (Continuous Integration, CI) consiste à faire exécuter la suite de tests par un serveur, automatiquement, à chaque modification publiée du code. Cette section montre comment le projet 5 barres s’y prend, et pourquoi chacun de ses choix est fait.

Note

Vous avez déjà mis en place une CI dans Publier la documentation : la publication automatique de la documentation sur GitHub Pages. Le mécanisme est le même (un workflow GitHub Actions) ; ce qui change ici est l’objet du contrôle — non plus produire un site, mais rendre un verdict sur le code.

Ce que la CI apporte réellement

  1. Elle exécute les tests, systématiquement. C’est la raison première, et elle suffirait.

  2. Elle les exécute dans un environnement propre. Votre machine contient des paquets installés il y a six mois, des variables d’environnement oubliées et un espace de travail à moitié compilé. La CI part d’une base vierge à chaque fois, et détecte donc les dépendances que vous avez oublié de déclarer — l’erreur la plus courante et la plus pénible dans un projet ROS.

  3. Elle rend le verdict public. Sur une pull request (voir Coopérer grâce aux pull requests), le relecteur voit immédiatement si la contribution casse quelque chose, sans avoir à récupérer la branche et à la compiler. La discussion peut alors porter sur le fond.

  4. Elle date les régressions. Un historique de CI indique le commit exact à partir duquel un test a commencé à échouer, ce qui transforme une enquête en une simple lecture.

  5. Elle protège la branche principale. On peut configurer GitHub pour interdire la fusion d’une branche dont la CI est rouge, ce qui garantit qu’une branche officielle reste toujours compilable et testée.

Important

Pour que ces promesses tiennent, une règle de discipline prime sur toute considération technique : une CI rouge est un problème que l’on traite immédiatement. Une équipe qui s’habitue à voir du rouge perd en quelques semaines tout le bénéfice de son investissement, et il ne lui reste qu’une facture de temps de calcul. C’est aussi pourquoi il faut à tout prix éliminer les tests instables (flaky) évoqués dans Écrire des tests C++ avec Google Test.

Première condition : un environnement reproductible

Le problème que Docker résout

Les tests du projet ont besoin de ROS 2 Jazzy, de MuJoCo (en Python et en C), de Google Test, de ros2_control, de xacro… Installer cela « à la main » sur le serveur de CI serait long, fragile et non reproductible : la version installée dépendrait du jour de l’installation.

C’est précisément le problème que résout une image Docker : une description exécutable d’un système complet, qui donne le même environnement sur le serveur de CI, sur votre machine, et sur celle de votre collègue — quelle que soit la distribution qu’il utilise.

Code source 45 docker/Dockerfile
# Image ROS 2 Jazzy + MuJoCo (Python ET C) + Google Test + système 5 barres.
#
# Build context = repository root (the image copies src/). From the repository root:
#   docker build -f docker/Dockerfile --target ci      -t five_bars:ci .   # headless (CI, tests)
#   docker build -f docker/Dockerfile --target desktop -t five_bars:dev .  # + RViz, GUI (X11)
# or simply: docker/start.sh   /   docker compose -f docker/docker-compose.yml build
#
# La bibliothèque C de MuJoCo utilisée par les tests gtest est celle livrée dans la roue
# pip `mujoco` (include/ + libmujoco.so.X.Y.Z) : Python et C++ utilisent EXACTEMENT la
# même version de MuJoCo. Pour utiliser une archive officielle à la place, définir MUJOCO_DIR.

ARG ROS_DISTRO=jazzy

# ----------------------------------------------------------------------------- base
FROM ros:${ROS_DISTRO}-ros-base AS base
ARG ROS_DISTRO
ARG MUJOCO_VERSION=4.0.1
ENV DEBIAN_FRONTEND=noninteractive \
    PYTHONUNBUFFERED=1

RUN apt-get update && apt-get install -y --no-install-recommends \
      build-essential cmake git python3-pip python3-numpy python3-yaml python3-pytest python3-tk \
      googletest libgtest-dev libgmock-dev \
      ros-${ROS_DISTRO}-ament-cmake-gtest \
      ros-${ROS_DISTRO}-ament-cmake-pytest \
      ros-${ROS_DISTRO}-ros2-control \
      ros-${ROS_DISTRO}-ros2-controllers \
      ros-${ROS_DISTRO}-xacro \
      ros-${ROS_DISTRO}-robot-state-publisher \
      ros-${ROS_DISTRO}-tf2-ros-py \
      libgl1 libegl1 libglfw3 libosmesa6 \
    && rm -rf /var/lib/apt/lists/*

# MuJoCo (Python + bibliothèque C embarquée dans la roue)
RUN pip3 install --no-cache-dir --break-system-packages "mujoco==${MUJOCO_VERSION}" \
 && MJ="$(python3 -c 'import mujoco, os; print(os.path.dirname(mujoco.__file__))')" \
 && ln -s "${MJ}" /opt/mujoco \
 && echo "${MJ}" > /etc/ld.so.conf.d/mujoco.conf && ldconfig \
 && python3 -c "import mujoco; print('MuJoCo', mujoco.__version__)" \
 && ls /opt/mujoco/include/mujoco/mujoco.h /opt/mujoco/libmujoco.so*
ENV MUJOCO_DIR=/opt/mujoco

WORKDIR /ws
COPY docker/entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh
ENTRYPOINT ["/entrypoint.sh"]
CMD ["bash"]

# ------------------------------------------------------------------------------- ci
# Workspace compilé, prêt pour `colcon test` (tout est headless).
FROM base AS ci
COPY src /ws/src
RUN . /opt/ros/${ROS_DISTRO}/setup.sh \
 && colcon build --event-handlers console_direct+ --cmake-args -DCMAKE_BUILD_TYPE=RelWithDebInfo

# -------------------------------------------------------------------------- desktop
# Pour le développement : RViz, outils graphiques et conversion CAO (trimesh).
FROM ci AS desktop
RUN apt-get update && apt-get install -y --no-install-recommends \
      ros-${ROS_DISTRO}-rviz2 ros-${ROS_DISTRO}-rqt-graph ros-${ROS_DISTRO}-rqt-plot \
      mesa-utils xvfb \
    && rm -rf /var/lib/apt/lists/* \
 && pip3 install --no-cache-dir --break-system-packages trimesh pycollada fast_simplification

Lisons-le à la lumière de ce qui précède.

Trois étages, pour trois usages

Le fichier définit une image en plusieurs étapes (multi-stage build), chaque étape prolongeant la précédente :

Étage

Usage

Contenu

base

commun

ROS 2, compilateur, Google Test, MuJoCo, dépendances système. Aucune dépendance graphique lourde.

ci

tests, CI

base + les sources copiées et déjà compilées. Entièrement headless.

desktop

développement

ci + RViz, outils rqt et bibliothèques de conversion CAO.

Ce découpage n’est pas une coquetterie. L’image de CI ne contient ni RViz ni serveur X : elle est donc plus petite, plus rapide à construire et plus rapide à télécharger, ce qui compte quand elle est reconstruite à chaque push. C’est la contrepartie directe du choix de tests headless expliqué dans Utiliser la simulation pour écrire des tests : parce que les tests n’ont pas besoin d’affichage, la CI n’a pas besoin d’en installer.

Figer les versions

Deux lignes méritent une attention particulière :

ARG ROS_DISTRO=jazzy

# ----------------------------------------------------------------------------- base
FROM ros:${ROS_DISTRO}-ros-base AS base
ARG ROS_DISTRO
ARG MUJOCO_VERSION=4.0.1

La version de MuJoCo est épinglée (MUJOCO_VERSION=4.0.1), et la distribution ROS aussi. Sans cela, une mise à jour de MuJoCo publiée un mardi matin pourrait faire échouer la CI d’un code que personne n’a modifié — l’un des échecs les plus déroutants qui soient, parce que rien dans l’historique du projet ne l’explique.

Astuce

Épingler les versions a une contrepartie : il faut les mettre à jour volontairement, de temps en temps, dans un commit dédié dont c’est le seul objet. Un tel commit a un énorme avantage : si la CI devient rouge, on sait exactement pourquoi, et on peut revenir en arrière en une commande.

Une seule version de MuJoCo pour les deux langages

La façon dont MuJoCo est installé mérite d’être soulignée :

# MuJoCo (Python + bibliothèque C embarquée dans la roue)
RUN pip3 install --no-cache-dir --break-system-packages "mujoco==${MUJOCO_VERSION}" \
 && MJ="$(python3 -c 'import mujoco, os; print(os.path.dirname(mujoco.__file__))')" \
 && ln -s "${MJ}" /opt/mujoco \
 && echo "${MJ}" > /etc/ld.so.conf.d/mujoco.conf && ldconfig \
 && python3 -c "import mujoco; print('MuJoCo', mujoco.__version__)" \
 && ls /opt/mujoco/include/mujoco/mujoco.h /opt/mujoco/libmujoco.so*
ENV MUJOCO_DIR=/opt/mujoco

L’installation se fait par pip, et la roue Python embarque à la fois le module Python et la bibliothèque C (include/ et libmujoco.so.X.Y.Z). Le ln -s et la ligne ld.so.conf.d rendent cette bibliothèque visible au compilateur et à l’éditeur de liens, et c’est elle que cmake/FindMuJoCo.cmake (voir Écrire des tests C++ avec Google Test) retrouve.

Conséquence : les tests C++ et les tests Python sont jugés par exactement la même version de l’oracle. C’est indispensable pour que la comparaison entre les deux implémentations, évoquée dans Écrire des tests pour du code Python, soit interprétable.

Notez aussi les deux dernières lignes de cette commande : elles vérifient que l’installation a réussi (le module s’importe, les fichiers attendus existent). Une image Docker qui échoue à la construction est un problème facile ; une image qui se construit en étant subtilement incomplète est un problème coûteux.

Le point d’entrée

Code source 46 docker/entrypoint.sh
#!/bin/bash
set -e
source "/opt/ros/${ROS_DISTRO}/setup.bash"
if [ -f /ws/install/setup.bash ]; then
  source /ws/install/setup.bash
fi
exec "$@"

Ce petit script garantit que toute commande lancée dans le conteneur dispose d’un environnement ROS initialisé — ce que l’on oublie une fois sur deux à la main, avec des messages d’erreur peu explicites à la clé.

Le workflow GitHub Actions

Voici le fichier qui décrit ce que fait le serveur à chaque modification :

Code source 47 .github/workflows/ci.yml
name: CI

on:
  push:
  pull_request:
  workflow_dispatch:

permissions:
  contents: read
  checks: write          # publication du rapport de tests
  pull-requests: write

jobs:
  build-and-test:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      - name: Image Docker (ROS 2 Jazzy + MuJoCo + gtest) et compilation du workspace
        uses: docker/build-push-action@v6
        with:
          context: .
          file: docker/Dockerfile
          target: ci
          tags: five_bars:ci
          load: true
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Tests unitaires headless (gtest + unittest + simulation MuJoCo)
        run: |
          mkdir -p test_results
          docker run --rm -v "$PWD/test_results:/ws/test_results" five_bars:ci bash -c '
            colcon test --event-handlers console_direct+ --return-code-on-test-failure; ret=$?
            colcon test-result --verbose
            cp build/*/test_results/*/*.xml /ws/test_results/ 2>/dev/null || true
            exit $ret'

      - name: Rapport de tests
        if: always()
        uses: EnricoMi/publish-unit-test-result-action@v2
        with:
          files: test_results/*.xml

      - name: Archive des résultats
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-results
          path: test_results/

Quand la CI se déclenche

on:
  push:
  pull_request:
  workflow_dispatch:

  • push : à chaque publication de commits, sur toutes les branches. C’est ce qui permet de travailler sur une branche en sachant en permanence où l’on en est.

  • pull_request : à chaque ouverture ou mise à jour d’une demande de fusion.

  • workflow_dispatch : ajoute un bouton pour lancer la CI à la main depuis l’interface de GitHub, ce qui est précieux pour vérifier qu’un échec était bien dû à une cause extérieure.

Les permissions

permissions:
  contents: read
  checks: write          # publication du rapport de tests
  pull-requests: write

Le workflow ne demande que ce dont il a besoin : lire le code, écrire un rapport de test et commenter une pull request. C’est l’application du principe de moindre privilège : un workflow qui n’a pas le droit d’écrire dans le dépôt ne peut pas le casser, même si l’une des actions qu’il utilise se révélait malveillante.

Les étapes

1. Récupérer le code et préparer le constructeur d’images.

      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

2. Construire l’image, ce qui compile le workspace.

      - name: Image Docker (ROS 2 Jazzy + MuJoCo + gtest) et compilation du workspace
        uses: docker/build-push-action@v6
        with:
          context: .
          file: docker/Dockerfile
          target: ci
          tags: five_bars:ci
          load: true
          cache-from: type=gha
          cache-to: type=gha,mode=max

Deux détails importants.

target: ci sélectionne l’étage headless : on ne construit pas RViz pour rien.

Les lignes cache-from / cache-to mettent en cache les couches de l’image chez GitHub. Sans elles, chaque exécution réinstallerait ROS, MuJoCo et toutes les dépendances — une dizaine de minutes à chaque push. Avec elles, seules les couches réellement modifiées sont reconstruites : comme les sources sont copiées à la fin du Dockerfile, une modification du code ne réinstalle rien.

Astuce

C’est la raison pour laquelle on place dans un Dockerfile les instructions de la plus stable à la plus changeante. Une ligne COPY src placée en haut du fichier invaliderait le cache de tout ce qui suit, et la CI deviendrait dix fois plus lente pour un résultat identique.

3. Exécuter les tests.

      - name: Tests unitaires headless (gtest + unittest + simulation MuJoCo)
        run: |
          mkdir -p test_results
          docker run --rm -v "$PWD/test_results:/ws/test_results" five_bars:ci bash -c '
            colcon test --event-handlers console_direct+ --return-code-on-test-failure; ret=$?
            colcon test-result --verbose
            cp build/*/test_results/*/*.xml /ws/test_results/ 2>/dev/null || true
            exit $ret'

Cette étape est le cœur du workflow, et chacun de ses morceaux a une raison d’être :

  • --return-code-on-test-failure : sans cette option, colcon test renvoie un code de succès même si des tests échouent ! La CI serait alors verte en permanence, ce qui est le pire des cas de figure. C’est l’erreur la plus fréquente dans une CI ROS 2 ;

  • ret=$? puis exit $ret : le code de retour est mémorisé avant les commandes suivantes, puis restitué à la fin, pour que le rapport et l’archive soient produits sans masquer le verdict ;

  • colcon test-result --verbose affiche le détail des échecs dans le journal de la CI, exactement comme la commande ros2_view_tests de Lancer les tests de ROS2 et les analyser le fait sur votre machine ;

  • les fichiers XML de résultats sont copiés dans un volume partagé, pour pouvoir être exploités par les étapes suivantes.

4. Publier un rapport lisible, et archiver les résultats.

      - name: Rapport de tests
        if: always()
        uses: EnricoMi/publish-unit-test-result-action@v2
        with:
          files: test_results/*.xml

      - name: Archive des résultats
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-results
          path: test_results/

Les fichiers XML produits par colcon sont au format JUnit, un format d’échange compris par tous les outils d’intégration continue. L’action publish-unit-test-result-action les transforme en un tableau lisible, directement visible sur la pull request : nombre de tests, lesquels ont échoué et avec quel message. Le relecteur n’a donc pas à lire le journal brut.

Le if: always() qui précède ces deux étapes est essentiel : par défaut, une étape est ignorée si une étape précédente a échoué. Or c’est exactement quand les tests échouent que l’on veut le rapport. Sans if: always(), la CI ne produirait de rapport que lorsqu’il n’y a rien à signaler.

Avertissement

Cette combinaison — --return-code-on-test-failure pour que l’échec compte, et if: always() pour que le rapport soit tout de même publié — est la partie délicate de toute CI de test. Une CI qui ne distingue pas « les tests ont échoué » de « la CI a échoué » ne sert à rien, et les deux erreurs symétriques (verte alors que les tests échouent, muette alors qu’ils échouent) sont faciles à commettre.

Exécuter la même chose sur sa machine

C’est la propriété la plus utile du dispositif, et celle qu’il faut rechercher dans tout projet : la CI ne fait rien que vous ne puissiez reproduire à l’identique chez vous.

Code source 48 docker/docker-compose.yml
# docker-compose.yml lives in docker/ ; every relative path is relative to this folder:
#   build context ".." = repository root, sources mounted from ../src.
#
# Usage (from the repository root):
#   xhost +local:docker                                   # allow X11 windows (Linux)
#   docker compose -f docker/docker-compose.yml build
#   docker compose -f docker/docker-compose.yml run --rm dev    # shell, ../src mounted in /ws/src
#   docker compose -f docker/docker-compose.yml run --rm test   # build + headless tests (like the CI)
# or from docker/:  cd docker && docker compose run --rm dev
services:
  dev:
    build:
      context: ..
      dockerfile: docker/Dockerfile
      target: desktop
    image: five_bars:dev
    network_mode: host
    ipc: host
    environment:
      - DISPLAY=${DISPLAY:-:0}
      - QT_X11_NO_MITSHM=1
      - ROS_DOMAIN_ID=${ROS_DOMAIN_ID:-0}
    volumes:
      - /tmp/.X11-unix:/tmp/.X11-unix:rw
      - ../src:/ws/src
    devices:
      - /dev/dri:/dev/dri   # GPU acceleration (remove if /dev/dri does not exist)
    command: >
      bash -c "colcon build --event-handlers console_cohesion- && source /ws/install/setup.bash && exec bash"

  test:
    build:
      context: ..
      dockerfile: docker/Dockerfile
      target: ci
    image: five_bars:ci
    volumes:
      - ../src:/ws/src
      - ../test_results:/ws/test_results
    command: >
      bash -c "colcon build --event-handlers console_cohesion+ &&
               colcon test --event-handlers console_direct+ --return-code-on-test-failure;
               ret=$$?; colcon test-result --verbose;
               mkdir -p /ws/test_results && cp build/*/test_results/*/*.xml /ws/test_results/ 2>/dev/null;
               exit $$ret"

Le service test est l’équivalent exact de la CI : même étage d’image (target: ci), mêmes options de colcon test, y compris le --return-code-on-test-failure qui donne son sens au verdict. La seule différence est qu’il recompile le workspace au démarrage, puisque les sources sont montées depuis votre machine au lieu d’être figées dans l’image.

# depuis la racine du workspace
docker compose -f docker/docker-compose.yml run --rm test

Le projet fournit également un script d’enrobage plus commode, qui construit l’image si elle manque :

docker/start.sh test      # compile, puis lance tous les tests, headless
docker/start.sh           # un shell dans le conteneur, workspace compilé
docker/start.sh --rebuild # forcer la reconstruction de l'image

Note

docker/start.sh test utilise l’image de développement (desktop) et non l’étage ci, et appelle colcon test sans --return-code-on-test-failure : il affiche donc le détail des tests, mais son code de retour ne reflète pas leur verdict. C’est le bon outil pour travailler ; pour vérifier exactement ce que dira la CI, utilisez le service test de docker compose.

docker/start.sh
Code source 49 docker/start.sh
#!/usr/bin/env bash
# Build the Docker image (if needed) and open a shell in the five-bar container.
#
# Can be called from anywhere (paths are resolved from this script's location):
#   docker/start.sh            build the image if missing, then open an interactive shell
#   docker/start.sh --rebuild  force a rebuild of the image, then open a shell
#   docker/start.sh test       run all unit tests headless (same as the GitHub CI)
#   docker/start.sh <cmd...>   run any command in the container, e.g. docker/start.sh ros2 run five_bars_mujoco direct_gui
#
# Layout: this script and docker-compose.yml live in docker/, the sources in ../src.
# The build context is the repository root (the image copies src/ into /ws/src).
#
# Your ../src folder is mounted in the container (/ws/src): edit on the host, then run
# `colcon build` in the container. The workspace is rebuilt automatically at startup.
set -euo pipefail

IMAGE="five_bars:dev"
CONTAINER="five_bars_dev"
DOCKER_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"   # .../five_bars_ws/docker
ROOT="$(cd "$DOCKER_DIR/.." && pwd)"                          # .../five_bars_ws (build context)
SRC_DIR="$ROOT/src"

if [[ ! -d "$SRC_DIR" ]]; then
  echo "Error: sources not found in $SRC_DIR (expected layout: docker/ and src/ side by side)." >&2
  exit 1
fi

if ! command -v docker >/dev/null 2>&1; then
  echo "Error: docker is not installed (https://docs.docker.com/engine/install/)." >&2
  exit 1
fi

# ---------------------------------------------------------------- build the image
REBUILD=0
if [[ "${1:-}" == "--rebuild" ]]; then
  REBUILD=1
  shift
fi
if [[ $REBUILD -eq 1 ]] || ! docker image inspect "$IMAGE" >/dev/null 2>&1; then
  echo ">>> Building image $IMAGE (first time: ~10 min)..."
  docker build -f "$DOCKER_DIR/Dockerfile" --target desktop -t "$IMAGE" "$ROOT"
fi

# ------------------------------------------------------------ what to run inside
BUILD_CMD="colcon build --event-handlers console_cohesion- --cmake-args -DCMAKE_BUILD_TYPE=RelWithDebInfo > /tmp/colcon_build.log 2>&1 \
  || { cat /tmp/colcon_build.log; echo '!!! colcon build failed'; }; source /ws/install/setup.bash"

if [[ $# -eq 0 ]]; then
  INNER="$BUILD_CMD; echo '>>> Workspace built. Try: ros2 run five_bars_mujoco direct_gui'; exec bash"
elif [[ "$1" == "test" ]]; then
  INNER="$BUILD_CMD; colcon test --event-handlers console_direct+; colcon test-result --verbose"
else
  INNER="$BUILD_CMD; exec $(printf '%q ' "$@")"
fi

# --------------------------------------------------- display (X11) and GPU options
DOCKER_ARGS=(--rm -it --name "$CONTAINER" --network host --ipc host
             -v "$SRC_DIR:/ws/src"
             -e "ROS_DOMAIN_ID=${ROS_DOMAIN_ID:-0}")

if [[ -n "${DISPLAY:-}" ]]; then
  # Allow local containers to open windows on your X server (Linux, also XWayland).
  if command -v xhost >/dev/null 2>&1; then
    xhost +local:docker >/dev/null 2>&1 || true
  fi
  DOCKER_ARGS+=(-e "DISPLAY=$DISPLAY" -e QT_X11_NO_MITSHM=1 -v /tmp/.X11-unix:/tmp/.X11-unix:rw)
else
  echo ">>> No DISPLAY: GUIs (MuJoCo viewer, sliders, RViz) will not open; headless use only."
fi
if [[ -e /dev/dri ]]; then
  DOCKER_ARGS+=(--device /dev/dri)   # GPU acceleration for the viewer (Intel/AMD)
fi

# A second docker/start.sh opens a new shell in the container that is already running.
if docker ps --format '{{.Names}}' | grep -qx "$CONTAINER"; then
  echo ">>> Container $CONTAINER is already running: opening another shell in it."
  exec docker exec -it "$CONTAINER" bash -c \
    'source /opt/ros/$ROS_DISTRO/setup.bash && source /ws/install/setup.bash && exec bash'
fi

exec docker run "${DOCKER_ARGS[@]}" "$IMAGE" bash -c "$INNER"

Deux différences entre les services dev et test du fichier compose méritent d’être relevées :

  • dev monte le serveur graphique X11 et le périphérique /dev/dri pour afficher le viewer MuJoCo et RViz ; test n’en a pas besoin, puisque les tests sont headless ;

  • dans les deux cas, ../src est monté dans le conteneur plutôt que copié : vous éditez le code sur votre machine, avec votre éditeur, et vous le compilez dans le conteneur.

Important

« Ça marche chez moi » cesse d’être un argument dès lors que vous pouvez lancer, en une commande, exactement ce que lance la CI. Avant d’ouvrir une pull request, exécutez docker/start.sh test : c’est le même verdict, obtenu quelques minutes plus tôt, et sans mobiliser le serveur.

Le cas particulier de ce projet : une CI rouge, volontairement

Rappelons l’état dans lequel le projet est livré : les tests existent, le code ne l’est pas, la CI est donc rouge.

Ce n’est pas une anomalie, c’est la traduction en CI du cycle TDD décrit dans Écrire des tests C++ avec Google Test. La CI y gagne un rôle supplémentaire, celui de tableau d’avancement : le rapport de tests publié à chaque push indique précisément combien de tests passent, et lesquels. Votre travail consiste à faire passer la CI du rouge au vert, et vous en mesurez l’avancement sans avoir à y penser.

Prudence

Un projet dont la CI est durablement rouge est un projet où plus personne ne lit la CI. Tant que cet état est volontaire et documenté — c’est le cas ici, le README du projet l’annonce — il est acceptable. Dans un projet en production, la règle est l’inverse : la branche principale doit toujours être verte, et le travail en cours se fait sur une branche.

Compléter la CI

Protéger la branche principale

Une CI qui rend un verdict que l’on peut ignorer n’est qu’une indication. Dans les réglages GitHub du dépôt (Settings → Branches → Branch protection rules), on peut exiger que la CI soit verte pour autoriser la fusion d’une pull request. C’est le complément naturel de la méthodologie de contribution décrite dans Coopérer grâce aux pull requests.

Vérifier aussi le style

Les tests de style (flake8, ament_cmake_copyright, formatage C++) sont exécutés par colcon test au même titre que les autres : la CI les contrôle donc déjà. Pour éviter de découvrir un problème de formatage après plusieurs minutes d’attente, mieux vaut le détecter avant de valider le commit, avec pre-commit : voir L’outil pre-commit.

La règle d’usage est la suivante : pre-commit sur votre machine pour un retour en une seconde, la CI comme filet de sécurité qui ne peut pas être contourné.

Quelques extensions utiles

  1. Une matrice de distributions : faire tourner le même workflow sur Humble et Jazzy, grâce à l’argument ROS_DISTRO déjà prévu dans le Dockerfile.

  2. La couverture de code (lcov pour le C++, coverage pour Python) : elle indique quelles lignes ne sont exécutées par aucun test. À lire comme un indicateur de ce qui n’est pas testé, et non comme une note à maximiser.

  3. Un délai maximal sur le job (timeout-minutes), pour qu’un test bloqué n’occupe pas un serveur pendant des heures.

  4. Une exécution planifiée (schedule) : lancer la CI chaque nuit détecte les ruptures venues de l’extérieur, sur un code que personne n’a modifié.

Exercices

  1. Reproduire la CI localement. Lancez docker compose -f docker/docker-compose.yml run --rm test. Comparez le nombre de tests passés et échoués avec ce qu’annonce le rapport de la CI sur GitHub. Les deux doivent coïncider : si ce n’est pas le cas, qu’est-ce que cela révèle ?

  2. Casser le verdict. Enlevez --return-code-on-test-failure du workflow, poussez la modification et observez. La CI est-elle verte ou rouge ? Combien de tests échouent réellement ? Pourquoi est-ce la panne la plus grave possible pour une CI ?

  3. Supprimer le rapport. Enlevez les deux if: always() et poussez. Que devient le rapport de tests quand les tests échouent ? Que reste-t-il pour diagnostiquer ?

  4. Mesurer le cache. Relevez la durée de l’étape de construction de l’image lors de deux exécutions successives, la seconde ne modifiant qu’un commentaire dans un fichier source. Expliquez l’écart. Que se passerait-il si la ligne COPY src /ws/src était placée juste après le FROM de l’étage base ?

  5. Épingler, ou pas. Remplacez MUJOCO_VERSION=4.0.1 par la dernière version disponible. Les tests passent-ils toujours ? Quel est l’intérêt, et quel est le risque, de ne pas épingler cette version ?

  6. Faire verdir la CI. Implémentez le modèle géométrique direct, dans les deux langages, et poussez sur une branche. Combien de tests deviennent verts ? Le rapport publié par la CI correspond-il à ce que vous attendiez ?
